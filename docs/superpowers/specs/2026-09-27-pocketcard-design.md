# PocketCard — спецификация MVP

**Версия:** 1.0 · **Дата:** 27 сентября 2026 года
**Проект:** PocketCard · **Предполагаемый репозиторий:** `pocketcard-ios`
**Статус:** согласованный проект реализован в исходниках для локальной передачи по запросу пользователя. Проверка настоящей iOS-сборки и Wallet на устройстве ещё не выполнена. Актуальный отчёт: `docs/VERIFICATION.md`. GitHub не изменяется; пользователь коммитит самостоятельно.

## 1. Цель и критерий результата

Пользователь создаёт персональные карточки из выбранной фотографии и/или произвольного текста, хранит редактируемые исходники в iPhone-приложении и добавляет подготовленные карточки в Apple Wallet.

Ключевая ценность — важное под рукой, а не создание билетов на вымышленные мероприятия или платёжных карт. Приложение не позиционируется как менеджер паролей, удостоверение личности или юридически действительный документ.

Первый результат: на личном iPhone можно создать карточку каждого из трёх видов, сохранить её, закрыть и открыть приложение, изменить содержимое, выпустить настоящий подписанный pass и добавить либо обновить его в Wallet. Проверки выполняются на вымышленных текстовых данных и несекретных изображениях. Опубликованное приложение в App Store — отдельный результат, не обещание этого MVP.

## 3. Важное уточнение: крупное фото в Wallet

При проверке актуальной документации обнаружена возможность, которую первоначальное обсуждение не учитывало: **Poster Generic для iOS 27 и новее**. Этот стиль предусматривает крупное фоновое изображение и не требует представлять карточку как билет на мероприятие. Классический `generic` остаётся совместимым вариантом для более ранних версий iOS. Apple описывает размещение `posterGeneric` и `generic` в одном pass для такой совместимости. [S1, S2]

**Предложение для этой спецификации:** сохранить три согласованных шаблона, но для шаблонов с фото выпускать оба представления. Для «Информации» достаточно классического `generic` на всех поддерживаемых версиях.

Это не означает свободную вёрстку: размеры, кадрирование и конечное расположение контролирует Wallet. Для классического Generic доступна миниатюра; обещание крупной фотографии к нему не относится. [S3]

Предлагаемая минимальная версия приложения — iOS 17. Полноценный фотоформат Wallet проверяется отдельно на iOS 27+. Наличие поддержки в документации не считается результатом испытаний на устройстве.

## 4. Шаблоны

| Шаблон | Обязательное для выпуска | В PocketCard | В Wallet |
|---|---|---|---|
| Фото | Заголовок и фото | Крупное фото; необязательная подпись | Poster Generic с фото на iOS 27+; миниатюра в классическом Generic |
| Информация | Заголовок и минимум одно заполненное поле | Текстовые поля, без фото | Классический Generic; краткая лицевая сторона и полные сведения в подробностях |
| Фото + информация | Заголовок, фото и минимум одно поле | Фото и текст в готовой композиции | Poster Generic с фото на iOS 27+; Generic с миниатюрой на более ранних версиях |

Изменение шаблона не удаляет ранее введённые данные. Неиспользуемые в выбранном шаблоне данные остаются локально, но **не экспортируются скрыто**. Например, переход с «Фото + информация» на «Фото» сохраняет поля в редакторе, но исключает их из передаваемого содержимого и `.pkpass`. Перед выпуском показано, какие сведения попадут в Wallet.

Для первого варианта оформления предлагаются четыре предустановленные темы с проверенными сочетаниями фона и текста. Выбор произвольного шрифта, собственная сетка и ручное позиционирование исключены.

## 5. Экраны и пользовательский сценарий

### 5.1. Мои карточки

Список карточек с названием, миниатюрой и состоянием. Сортировка по последнему изменению. В пустом состоянии — объяснение назначения и кнопка «Создать карточку». На списке не показываются значения пользовательских полей, чтобы случайно не раскрывать секреты.

Доступные действия: открыть, редактировать, создать копию, удалить. Копия получает новый идентификатор; изменение копии не обновляет исходную карточку в Wallet.

### 5.2. Выбор шаблона

Три примера: «Фото», «Информация», «Фото + информация». Для шаблонов с фото сразу объясняется отличие нового и классического отображения Wallet. Пользователь не выбирает технические типы вроде `eventTicket`.

### 5.3. Редактор

Редактор содержит заголовок, выбор шаблона, выбор фото, кадрирование, подпись, поля и тему. Набор видимых элементов зависит от шаблона.

Поля добавляются и удаляются; порядок соответствует порядку ввода. Свободного перетаскивания нет. Все значения — строки: приложение не преобразует код с ведущими нулями в число и не пытается определить пароль по названию поля.

Сохранение выполняется явно. Неполную карточку разрешено сохранить как черновик; выпуск доступен только после проверки обязательных данных. При выходе с несохранёнными изменениями предлагается сохранить или отменить изменения.

### 5.4. Просмотр карточки

Показываются выбранная композиция и полные локальные данные. Доступны редактирование и переход к выпуску. Изображение открывается крупно внутри приложения; это не обещание такого же масштаба в Wallet.

### 5.5. Предпросмотр и выпуск

Сначала показывается ориентировочный вид Wallet, пояснение совместимости и полный перечень экспортируемых данных. Для фотошаблонов доступны примеры современного и классического отображения.

После подтверждения передачи данных приложение получает подписанный pass и открывает системный `PKAddPassesViewController` для окончательного просмотра и добавления. Этот контроллер предназначен именно для показа pass и решения пользователя о добавлении. [S4]

Пользовательский сценарий:

**Мои карточки → Создать → Шаблон → Редактор → Сохранить → Предпросмотр → Подтвердить передачу → Выпустить → Системный экран Wallet.**

## 6. Отображение текстовых полей

Для предсказуемого первого варианта предлагаем не более двух пользовательских полей на лицевой стороне. Это **ограничение PocketCard**, а не заявление о максимуме Apple. Остальные сведения размещаются в подробностях; полные значения первых двух полей также дублируются там с отдельными техническими ключами.

Очень длинное значение на лицевой стороне заменяется подписью «См. подробности». Исходный текст сохраняется полностью и не обрезается в подробностях. В предпросмотре такие поля явно отмечены. Wallet может уменьшать или скрывать текст при недостатке места, поэтому ориентировочный предпросмотр не объявляется пиксельно точным. [S3]

У «Фото» дополнительные поля не экспортируются. Подпись, если она есть, размещается в подробностях; лицевая сторона содержит название и изображение. У «Фото + информация» подпись также попадает в подробности.

Технические ключи генерируются из идентификатора поля, а не из введённой подписи. Изменение подписи не меняет идентичность поля. Зарезервированные ключи издателя недоступны для редактирования пользователем.

## 7. Предлагаемые лимиты MVP

| Данные | Ограничение продукта |
|---|---|
| Заголовок | До 60 символов |
| Подпись | До 500 символов |
| Пользовательские поля | До 10 на карточку |
| Название поля | До 40 символов |
| Значение поля | До 2 000 символов |
| Значение на лицевой стороне | До 80 символов, иначе «См. подробности» |
| Исходный импорт изображения | До 25 MiB и 50 мегапикселей |
| Текстовые метаданные запроса | До 64 KiB в UTF-8 после сериализации |
| Полный запрос выпуска | До 5 MiB |

Лимиты повторно проверяются сервером. Превышение вызывает понятное сообщение; данные не обрезаются молча. Размер изображения проверяется до полного декодирования. Большая фотография уменьшается локально до подготовленных вариантов, а не отправляется на сервер в исходном размере.

## 8. Модель данных и локальное хранение

Карточка содержит: `id`, `schemaVersion`, `template`, `title`, `caption`, `fields`, `theme`, ссылки на локальное фото, параметры кадрирования, `createdAt`, `updatedAt`, `revision` и метаданные последнего выпуска.

Поле содержит `id`, `label`, `value`. Версия содержимого увеличивается при сохранённом изменении данных или оформления. Метаданные выпуска хранят ревизию, контрольную сумму экспортируемого содержимого и идентификаторы pass, но не сертификаты.

Для MVP предлагается файловое хранилище: JSON для карточек и отдельные файлы изображений в закрытом каталоге приложения. Доступ оформляется через `CardRepository`, чтобы интерфейс не зависел от формата хранения.

Новые изображения сохраняются под новыми идентификаторами до замены JSON. JSON записывается атомарно; предыдущие изображения удаляются только после успешного сохранения ссылки на новую версию. Незавершённая запись не должна разрушать предыдущую карточку. Сломанная запись обрабатывается отдельно и не превращает всю библиотеку в пустую.

Для файлов назначается полная системная защита данных: чтение и запись недоступны приложению, пока устройство заблокировано. Такое назначение поддерживается средствами Foundation. [S5] Это не отдельное защищённое хранилище паролей и не защита от человека с доступом к разблокированному приложению.

Изображение выбирается через системный PhotosPicker: доступ предоставляется выбранному пользователем объекту, без запроса всей фотобиблиотеки. [S6] Приложение хранит собственную рабочую копию для повторного кадрирования. Геометки и другие EXIF-метаданные исключаются из экспортируемых изображений. Исходное фото в приложении «Фото» не изменяется.

Пользовательская iCloud-синхронизация и собственное восстановление библиотеки не входят в MVP. Нельзя описывать весь продукт фразой «данные никогда не покидают устройство»: выпуск требует передачи серверу, а Wallet хранит отдельную копию.

## 9. Архитектура

Предлагаемые части iOS-приложения:

- **Интерфейс:** библиотека, выбор шаблона, редактор, просмотр и выпуск.
- **Модель и правила:** карточка, проверка значений, отображение и состав экспорта.
- **Хранилище и изображения:** локальная запись, импорт, кадрирование и уменьшение.
- **Wallet:** сетевой клиент выпуска и адаптер PassKit.

Сервис подписи — отдельный HTTP-компонент. Предлагаемый стек для первой реализации: Python, FastAPI и библиотека CMS/PKCS#7-подписи; конкретные поддерживаемые версии фиксируются в плане реализации и зависимостях. iOS-код не зависит от языка сервиса, только от его контракта.

Варианты архитектуры рассмотрены так: внешний сервис выбран как основной; локальная подпись с вшитым закрытым ключом исключена; отдельная утилита подписи на Mac допустима для ранней проверки, но не заменяет согласованный пользовательский сценарий приложения.

## 10. Контракт сервиса выпуска

**Операция:** `POST /v1/passes`. Передаются структурированные метаданные и подготовленные растровые изображения. Ответ при успехе — бинарный `.pkpass` с типом `application/vnd.apple.pkpass` и `Cache-Control: no-store`.

Метаданные включают версию схемы, идентификатор карточки, ревизию, выбранный шаблон, название, подпись, применимые поля, тему и контрольную сумму экспорта. Данные, скрытые текущим шаблоном, не передаются.

Сервис самостоятельно определяет `teamIdentifier`, `passTypeIdentifier`, сведения издателя и технические ключи. Он не принимает произвольный `pass.json`, ZIP, файловые пути, внешние ссылки на изображения или сертификат от клиента. Тип выпуска ограничен согласованными Generic/Poster Generic; нельзя запросить другой вид pass.

Последовательность обработки: проверить доступ → проверить лимиты и схему → подготовить пакет → подписать → вернуть результат. Фото и текст не сохраняются в базе, очереди, объектном хранилище или журналах. Обработка происходит в памяти; при ошибке и после ответа ресурсы освобождаются. Конфигурация инфраструктуры также должна исключать запись тел запросов и ответов на диск и в трассировки.

При этом **сервер видит переданное содержимое в открытом виде во время обработки**. Отсутствие постоянного хранения не является сквозным шифрованием или доказательством мгновенного криптографического стирания памяти.

Для личной тестовой сборки используется отдельный отзываемый токен установки, вводимый один раз в диагностических настройках и сохраняемый в Keychain. Токен не вшивается в приложение и не попадает в GitHub. Публичный анонимный сервис подписи исключён. Предлагаемые стартовые ограничения: один одновременный выпуск и не более 10 запросов в минуту на токен.

На сервере используются сертификат Wallet, соответствующий закрытый ключ и промежуточный сертификат Apple. Создание pass требует корректного идентификатора и сертификата; выпуск — подписанного пакета с manifest. [S7, S8] При отсутствии или истечении сертификата сервис отказывает в выпуске, а не возвращает неподписанную имитацию.

Секреты размещаются вне репозитория и образа приложения. Проверки кода не должны требовать настоящий production-ключ. Сборки pull request не получают сертификаты.

## 11. Состояния, добавление и обновление

Необходимо разделить три понятия: готовность локального черновика, успешность выпуска и фактическое наличие версии в Wallet.

| Состояние | Значение |
|---|---|
| Черновик | Карточка сохранена, но обязательные данные для выпуска неполны |
| Готова к добавлению | Проверка пройдена; наличие актуальной версии в Wallet не подтверждено |
| Выпускается | Выполняется единственный активный запрос для снимка содержимого |
| В Wallet | Наличие соответствующего pass подтверждено через PassKit |
| Есть изменения | В приложении сохранена более новая версия |
| Ошибка выпуска | Текущая попытка завершилась ошибкой; локальные данные сохранены |
| Статус Wallet недоступен | Приложение не смогло проверить библиотеку; успех не предполагается |

Для добавления сначала проверяется `PKAddPassesViewController.canAddPasses()`. Наличие библиотеки Wallet само по себе не является этой проверкой. [S9]

Полученный pass проверяется на ожидаемые идентификаторы и соответствие снимку запроса. Если пользователь изменил карточку во время ожидания, старый ответ не делает новую ревизию актуальной: предлагается выпустить текущую версию.

Закрытие системного экрана не означает добавления. После закрытия проверяется библиотека. Для чтения и обновления предусматриваются права на собственный Pass Type ID; широкие права на чужие карточки не нужны.

Повторный выпуск сохраняет pass type и серийный номер. Обновление запрашивается явной кнопкой «Обновить в Wallet»; используется `replacePass(with:)` с проверкой результата. Apple определяет замену по совпадению этих идентификаторов. [S10] При отсутствии pass предлагается обычное добавление. Автоматические push-обновления и синхронизация с другими устройствами не входят в MVP.

Локальное удаление не удаляет pass из Wallet. Диалог сообщает: «Карточка будет удалена из PocketCard. Копия в Apple Wallet останется». Для MVP удаление Wallet-копии выполняется пользователем в самом Wallet. После удаления локальных исходников приложение не обещает восстановить их из pass.

## 12. Конфиденциальность и тексты интерфейса

Перед каждым новым выпуском или обновлением показывается краткое подтверждение:

> Для создания карточки текст и подготовленное фото будут переданы сервису PocketCard. Сервис получает доступ к ним во время обработки. Карточка Wallet не является защищённым хранилищем паролей.

Кнопки: «Продолжить» и «Отмена». До подтверждения сетевой запрос с содержимым не отправляется. Экран должен показывать фактического оператора и адрес сервиса; тестовая сборка без этих настроек сохраняет карточки, но не выпускает их.

Подпись `.pkpass` подтверждает целостность и издателя, но не шифрует текстовые поля или изображения пакета. Это вывод из описанной Apple структуры подписанного ZIP-пакета. [S8] Нельзя показывать декоративные звёздочки так, будто реальное значение защищено в Wallet. Имена полей не анализируются ИИ; специального режима паролей в MVP нет.

У приложения нет аналитики содержимого и сторонних crash-логов с пользовательскими данными. Экран с открытой карточкой закрывается нейтральной заставкой в снимке переключателя приложений. Обычный снимок экрана или фотографирование чужим устройством не объявляются предотвращёнными.

Примеры ошибок:

| Ситуация | Сообщение и действие |
|---|---|
| Нет сети / сервис недоступен | «Карточка сохранена. Выпуск в Wallet сейчас недоступен. Повторите попытку позже» |
| Ошибка изображения | «Выберите другое изображение. Исходная карточка сохранена» |
| Недостаточно места | «Освободите место на устройстве и повторите сохранение»; редактор остаётся открытым |
| Ошибка подписи | «Сервис выпуска требует настройки. Карточка сохранена в приложении» |
| Wallet недоступен | «Добавление в Wallet на этом устройстве недоступно» |
| Пользователь отменил добавление | Возврат к карточке без сообщения об ошибке и без ложного статуса «В Wallet» |

Серверные ошибки имеют безопасный машинный код. В пользовательском ответе не возвращаются стек вызовов, сертификаты, содержимое запросов или внутренние пути.

## 13. Границы публикации

App Review Guidelines 3.2.1(iv) ограничивают назначения Wallet-карточек; техническое появление Poster Generic не отменяет эти правила. Одобрение приложения для произвольных личных фотографий и заметок остаётся неопределённым. [S11]

Приложение и описание должны честно объяснять назначение. Запрещено маскировать личную заметку под действительный билет, пропуск или удостоверение ради обхода проверки. Название PocketCard пока рабочее: проверка товарных знаков, домена и доступности названия не выполнена.

Публичный релиз допускается только после отдельной проверки правил использования Wallet, защиты публичного сервиса подписи, политики обработки данных и готовности Apple Developer-конфигурации. Личный тест не считается разрешением Apple на любой сценарий.

## 14. Проверки и критерии приёмки

| Область | Проверяемый результат |
|---|---|
| Три шаблона | Можно создать и сохранить каждый вариант с нужным составом данных |
| Смена шаблона | Данные сохраняются локально; скрытое содержимое отсутствует в запросе и pass |
| Перезапуск | Сохранённая карточка и фото доступны после закрытия приложения |
| Сбой записи | Предыдущая сохранённая версия остаётся читаемой |
| Изображения | Работают портретные и горизонтальные фото, ориентация и повторное кадрирование; EXIF не экспортируется |
| Поля | Кириллица, emoji, ведущие нули, длинные значения и лимиты не искажают исходные данные |
| Новый Wallet | На iOS 27+ проверен настоящий Poster Generic с крупным изображением |
| Совместимость | Более ранняя поддерживаемая iOS принимает классический Generic того же фотошаблона |
| Добавление | Отмена системного экрана не отмечается как успех |
| Обновление | Новая версия заменяет исходный pass, а не создаёт дубликат |
| Параллельные действия | Повторные нажатия не запускают несколько выпусков; устаревший ответ не перезаписывает актуальную ревизию |
| Нет сети / неверный сертификат | Карточка сохраняется; выдана понятная ошибка без утраты данных |
| Конфиденциальность | До подтверждения нет передачи содержимого; серверные логи не содержат фото, полей или токенов |
| Безопасность сервиса | Неверный токен, превышение лимитов и неподдерживаемый пакет отклоняются |
| Удаление | Удаление в PocketCard не удаляет копию Wallet и явно объясняет это |
| Доступность | VoiceOver и увеличенный размер текста позволяют пройти основной сценарий |

Модульные тесты покрывают модель, валидацию, проекцию шаблонов и обработку состояний. Интеграционные — API, состав пакета и подпись на тестовых ключах. Окончательная проверка Apple Wallet выполняется с действительным сертификатом на устройстве; макет и успешная проверка ZIP её не заменяют.

## 15. Не входит в MVP

Не включены свободный графический редактор, генерация и сканирование QR, импорт чужих pass, OCR документов, NFC, Apple Pay, автозаполнение паролей, отдельный Face ID-сейф, iCloud-синхронизация, семейный доступ, регистрация пользователей, покупки, реклама, аналитика и push-обновления Wallet.

Apple Watch не является целевой платформой проверки первой версии. Отображение на часах не обещается идентичным iPhone. [S1]

## 16. Зависимости перед реальным выпуском

Потребуются доступ к сертификатам Apple Developer, зарегистрированный Pass Type ID, сертификат с закрытым ключом, сведения издателя и HTTPS-сервис. Наличие аккаунта Apple Developer само по себе не подтверждает наличие всех этих настроек. Инструкция Apple описывает регистрацию идентификатора и выпуск сертификата отдельно. [S7]

Ни пароль Apple Account, ни закрытый ключ, ни токен GitHub не нужно присылать в чат или добавлять в репозиторий. Отсутствие сертификатов не блокирует разработку локальной библиотеки и редактора, но блокирует заявление, что выпуск в Wallet проверен.

Следующий артефакт после рассмотрения этой спецификации — план реализации с конкретными файлами, зависимостями и проверками. Текущий файл не является готовым Xcode-проектом или подтверждением публикации в GitHub.
